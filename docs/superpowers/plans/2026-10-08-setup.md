# Setup del plugin: plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un `setup` interactivo de nueve pasos que deja el cliente web accesible con contraseña y HTTPS (por túnel) y persistente tras reinicios, más el endurecimiento del servidor que exige exponerlo.

**Architecture:** El servidor Bun gana un módulo `server/access.ts` que decide, por petición, si confía en cabeceras de proxy y si `Host`/`Origin`/transporte son aceptables; las sesiones se guardan hasheadas y el límite de login vive en su módulo. El asistente de setup se parte en módulos puros y testeables bajo `scripts/setup/` (env, preflight, túnel, servicio, verificación, resumen) orquestados por `scripts/setup/wizard.ts`; `scripts/plugin.ts` solo despacha verbos.

**Tech Stack:** Bun 1.3+, TypeScript estricto, `bun test`, `qrcode-generator` (QR ASCII), CLIs externas `tailscale`, `portal`, `systemctl`, `launchctl`.

**Spec:** `docs/superpowers/specs/2026-10-08-setup-design.md`

## Global Constraints

- Solo Bun; nada de Node ni `npm`. Imports con extensión `.ts`; `verbatimModuleSyntax`.
- Textos que ve el usuario en español; código, comentarios y mensajes de commit en inglés.
- Estado de usuario en `HERDR_PLUGIN_CONFIG_DIR` (`.env`, `auth.json`), runtime en `HERDR_PLUGIN_STATE_DIR` (pid, `sessions.json`, log). Nunca en el root del plugin.
- Archivos con secretos o sesiones: modo `0600`.
- La contraseña nunca viaja por argv ni por HTTP para fijarse.
- Claves de `.env`: `ACCESS_MODE` ∈ {`local`,`lan`,`remote`}, `HOST`, `PORT`, `PUBLIC_URL`, `TUNNEL` ∈ {`tailscale`,`portal`}.
- Puerto por defecto `7340`.
- Cada paso del setup es idempotente.
- Cada commit termina con las líneas de atribución que indique la sesión (Co-Authored-By / Claude-Session).

## Review Focus

1. Petición con `X-Forwarded-For` falsificado desde un peer no loopback: debe contarse contra la IP del peer, no contra la inventada. Test en Task 2.
2. `Host` con puerto distinto al de `PUBLIC_URL` o con mayúsculas: `localhost:5173` (Vite dev) y `LOCALHOST` deben pasar; `evil.com` no. Test en Task 2.
3. `sessions.json` antiguo con ids en claro (formato previo a H5): el servidor debe arrancar, ignorar esas entradas y no romper. Test en Task 3.
4. `tailscale funnel` cuando Funnel no está habilitado en el tailnet: la salida trae un link; el setup debe mostrarlo y esperar, no fallar. Test de parser en Task 6.
5. `setup` repetido con todo ya hecho: ningún paso debe reescribir unidades idénticas ni reiniciar el túnel; el resumen debe salir igual. Test de `renderUnit` estable en Task 7 y verificación manual en Task 8.

**Interfaces:**
